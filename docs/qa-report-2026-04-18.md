## Bugs found + fixed inline

### BUG #1 — Celery worker image missing scan tools + Python deps

**Severity:** Critical — pipeline could not execute a single scan in production.

**Symptom:** Launching `POST /api/scans/` for a Full Scan → scan row enters `running`,
Celery task picks it up, immediately fails with `ModuleNotFoundError: No module
named 'rich'`. Even after fixing that, `FileNotFoundError: nmap` / `nuclei` /
`httpx` would follow.

**Root cause:** `web_portal/Dockerfile` is a minimal python:3.12-slim image that
installs only Django+Celery requirements from `web_portal/requirements.txt`. It:

1. Did NOT `pip install -e /app/src` the `wireghost` scanner package, so its
   pyproject-declared runtime deps (`rich`, `aiohttp`, `defusedxml`) never landed.
2. Did NOT apt-install or COPY any scan binaries (nmap, nuclei, httpx, naabu,
   masscan, fping, searchsploit, wpscan). The pipeline subprocesses to these
   tools directly — no binary → immediate FileNotFoundError.

The separate `callmedemon/wireghost` image (root `Dockerfile`) DOES have all
the tools, but Celery worker never ran inside that image. So every scan from
the first day of this deployment would have failed with one of those two
errors. Silent failure mode because tasks' try/except logs but doesn't surface.

**Fix (commit `7af2376`):**
- `web_portal/requirements.txt` — add `rich>=13.0`, `aiohttp>=3.9`, `defusedxml>=0.7`.
- `web_portal/Dockerfile` — convert to a 2-stage build:
  - Stage 1 pulls latest nuclei/httpx/naabu Go binaries from GitHub releases.
  - Stage 2 apt-installs `nmap fping masscan git libpcap0.8`, copies the
    pd-tools binaries, shallow-clones `exploitdb` for `searchsploit`.

**Verification after fix:**
```
$ docker compose exec worker which nmap nuclei httpx naabu fping searchsploit
/usr/bin/nmap
/usr/local/bin/nuclei
/usr/local/bin/httpx
/usr/local/bin/naabu
/usr/bin/fping
/usr/local/bin/searchsploit

$ docker compose exec worker python -c 'import rich'   # no ImportError
```

Settings → Tools tab now reports **7/9 tools Found** with real version strings.

**Still missing in image:**
- **WPScan** — Ruby gem; install would need `ruby-dev` + `gem install wpscan`. Not
  blocking for 95.111.251.53 (no WordPress fingerprinted).
- **scannerctl** — OpenVAS Rust binary; requires a separate Rust builder stage
  with `libpcap-dev libssl-dev libclang-dev clang` + `cargo build`. The root
  Dockerfile has this at stage 2 but it's ~10 min of build time. Not blocking.

Both can be added in a follow-up if full-pipeline coverage is desired.
